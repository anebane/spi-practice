# 作業ルール（spi-practice の全エージェント共通）

> このファイルは**毎回の指示に書かれない代わりに、作業前に必ず読む**もの。
> 指示側は「性質の一文＋今回だけの条件」だけを渡す。

## 報告の形（これを守ると往復が減る）

```
1行目   N件中M件 / EXIT=? / ブランチ先端のハッシュ
2行目   判断を仰ぐことがあれば1つだけ。無ければ「判断待ちなし」
以降    ⚠️ 想定と違ったこと・自分のミス・未再現の事象だけ
```

⚠️ **同意されるだけの説明を書かない。**設計判断の根拠は、コードのコメントかコミットメッセージに残す。
⚠️ **詳細はファイルに書き、報告には場所だけ書く。**指示側は必要なときに読む。

## 測り方

- **件数は必ず「N件中M件」**。分母を出す。⚠️ 0件のときは**分母と、空回りしていないことの証拠**を添える
- ⚠️ **`grep` の一致を「無い証拠」に使わない。**動作で測る（潰して落ちるか）
- ⚠️ **壊し方の強さを申告する。**「丸ごと空にする」で落ちない件数と「1要素だけ変える」で落ちない件数は別物
- ⚠️ **検査の出力と比べるなら、その検査を実行する。**簡易版を自作して比べない（試行回数とキーが必ずずれる）
- **実測していないものは「見立て」と明記。**推測で埋めない
- ⚠️ **再現できていないものを「直った」と言わない**
- ⚠️ **対になる数字を並べて出す。**開始と終了、表示とクリック、送信と受信。片方だけだと壊れていても気づけない
  （実績: `exam_finish` が `exam_start` を上回っていたのに、完走率として数字は出ていた）
- ⚠️ **母集団を分けてから数える。**まとめられないものが混ざっていないか先に確認する
  （実績: 4択と5択を混ぜて数え、実在しない偏りを3件のうち2件「発見」した）
- ⚠️ **「ありえない0」を探す。**0が出たら、同じ画面で0のはずがない項目を見る。それも0なら数えられていない
  （実績: GSCの外部リンク0件。内部リンクも0件で、計測されていないだけだった）
- ⚠️ **期間を変えて2回測る。**近ければ傾向、大きく違えば単発
  （実績: 同じ流入元が 35日で31、28日で9。継続と読んだが実際は一度跳ねて減衰していた）
- ⚠️ **行動データの0を、利用者の意思の結果と解釈しない。**その行動が成立する状態だったかを先に確認する
  （実績: シェア0回を心理の問題と解釈していたが、og:image が無く共有カードが空だった）
- ⚠️ **UI操作は「押した」で終わらせず、結果を別の手段で確かめる。**
  （実績: 2026-09-05にGSCの索引リクエストをJSの `.click()` で8件送ったつもりが、
   実際は1件も通っていなかった。要素が button でなく span で、Googleのハンドラは
   実マウス操作を待っていた。APIで索引状態を見るまで気づけなかった）
  ⚠️ **セレクタは前回動いた形が今回も動くとは限らない。**同じ画面でもボタンがリンクに変わる

## 検証

- ⚠️ **`EXIT=1` は「何かが落ちた」であって「狙ったものが落ちた」ではない。**狙った失敗メッセージが出るところまで見る
- **足したあと全件を回す。**単独実行では緑のまま壊れていることがある（実績多数）
- ⚠️ **ローカルの緑は CI の緑ではない。**環境差で落ちる（実績: Python依存がCIに無く、半日CIが落ちていた）
- **検査を足したら変異も足す。**未カバーだと検出器が EXIT=1 にする
- ⚠️ **コミット前に必ず `node test/mutation-runner.js --check-mutations` を通す。**
  変異台帳の `find` はソースの文字列そのままなので、**コードを動かすと黙って壊れる。**
  数秒で終わるのに、忘れると「変異が当たっていないのに緑」という最悪の状態が入る
  （実績: 2026-09-06に壊れたままコミットした。プロファイルを2つにしたら
   同じ行が2箇所になり `find` の一意性が崩れた）
  → 特に **既存の宣言をコピーして2つ目を作ったとき**は、ほぼ確実に一意性が壊れる
- ⚠️ **コードを別の場所へ移したとき、「緑」は移行できた証拠にならない。**
  旧経路が残っていれば、移行が1つも効いていなくても全部緑になる（2026-09-06に実際に騙された）。
  → **新しい経路が何回呼ばれたかを実測する。**0回なら効いていない
  → **旧を消す前に、同じ入力で新旧を走らせて突き合わせる。**不一致0を確認してから消す
  → 乱数が絡むならシードを固定して、消費パターンごと揃える
- ⚠️ **イベント名・関数名を推測で決めて探さない。**無いものを探せば当然0件で、
  それを「計測漏れ」と読むと存在しない不具合を報告することになる
  （実績: 2026-09-06に `share_click` で探して0件→「計測されていない」と報告。
   実際は `share_x` で90日7件あった。関数も途中までしか読んでいなかった）
  → **先に一覧を取る**（GA4ならイベント名の一覧、コードなら関数を最後まで読む）
- ⚠️ **JSのオブジェクトは同じキーを2回書いてもエラーにならない。あとの定義が黙って勝つ。**
  （実績: 2026-09-06に `derive` を手とスクリプトの両方から入れて3本が二重定義。
   生成結果は正しいので全検査が緑のまま通った）
  → 自動で挿入したら、**挿入した数と実際に効いている数を突き合わせる**
- ⚠️ **`until ! pgrep -f X` で待つと、待機コマンド自身が `pgrep -f X` に引っかかる。**
  自分を検出して永久に待ち続け、「まだ実行中」と誤認したまま何時間も進む
  （実績: 2026-09-06に待機ループ2本が4時間回り続け、その間ずっと
   「ランナー実行中」と判断していた。実際のランナーはとうに完走していた）
  → 待つなら **`run_in_background` でコマンド自体を投げる**。自作の待機ループを書かない
  → どうしても `pgrep` するなら **`pgrep -f "node test/mutation-runner"`** のように実体だけに当てる
- ⚠️ **長い処理をタイムアウトさせると、シェルは死ぬが node は生き残る。**
  変異ランナーのようにファイルを書き換えて戻すツールでは、**残骸が次の実行と衝突する。**
  （実績: 2026-09-06に2つ同時に走り、相手の変異を検知して中断。作業ツリーに変異が残った）
  → 起動前に **`pgrep -f mutation-runner`** で先客を確かめる
  → 最初から **バックグラウンド実行**にする。前景で走らせて2分で切るのが事故の入口
  → 中断されたら **`git status` の前に `git update-index --really-refresh`**。statキャッシュが「クリーン」と嘘をつく

## リポジトリを書き換える道具は、殺されても戻るように書く

⚠️ 変異を1件ずつ当てて確かめる道具は、**当てている最中にリポジトリが壊れた状態**になる。
前景実行はツールのタイムアウトで SIGTERM/SIGKILL を受けるので、そこで止まると壊れたまま残る。

2026-09-07に踏んだ: 10件を前景で回して2分で殺され、`UNIT_LABELS` から `"通り"` が
**消えたまま**先へ進んだ。次の全検査で初めて気づいたが、その間に測った結果は全部
「単位が1件足りない状態」のものだった。

- 後始末を `process.on("exit" / "SIGINT" / "SIGTERM" / "SIGHUP" / "uncaughtException")` に登録する
- **時間のかかる検証はバックグラウンドで回す**（前景は2分で切られる）
- ⚠️ **道具が落ちたあとは `git diff` を見る。**「途中で終わった」と「途中で壊した」は違う

## ブラウザで確かめるときは、先に Service Worker を消す

⚠️ このサイトは PWA で、`sw.js` が `/`・`/questions.js`・`/generator.js`・`/app.js` などを
**プリキャッシュしている**。`VERSION` を上げない限り、再訪問者にも自分にも**旧版が配られ続ける**。
「2回目で直る」ではなく**永久に直らない**（`caches.match` はキャッシュを作成順に検索するため）。

2026-09-07に**1日で5回**これに騙された。いちばん危なかったのは、
Node の検査が全部緑・プロファイル経由の生成も完全な英語なのに、
**ブラウザで開いたら日本語の問題が出た**とき。数分「重大なバグだ」と誤認した。
実際は起動時に取り込まれた古い `questions.js` を見ていただけだった。

⚠️ **開発中は `VERSION` を上げても足りない。**1回上げたあと編集を続けると、
その間に開いたブラウザが「新しい VERSION 名の、古い中身」を抱える。名前が同じなので消えない。

**測る前に必ずこれを実行する**（Playwright の `browser_evaluate` で）:

```js
const regs = await navigator.serviceWorker.getRegistrations();
for (const r of regs) await r.unregister();
for (const n of await caches.keys()) await caches.delete(n);
```

そのうえでクエリを変えて（`?fresh=1`）読み直す。
- **画面の見た目がおかしいときも、まずこれを疑う。**CSSもプリキャッシュ対象
- ⚠️ **「直したのに直らない」を実装のせいにする前に、キャッシュを消して測り直す。**
  今日は逆に「壊れている」と誤認した側で踏んだ

## 「落ちた」ではなく「どの検査が落ちたか」を見る

⚠️ 変異を当てて `EXIT=1` が返っても、**狙った検査が落ちたとは限らない。**
別の検査が拾っているだけで、名指しの検査は対象外のまま素通りしていることがある。

2026-09-08、独立検証で発覚した。`table_ratio_01` の答えを1種類に潰す変異を当てたら
スイートは赤になったが、落ちたのは「答えの偏りが大きすぎる」検査であって、
確かめたかった「正解の中身の偏り」検査は**そのテンプレートを一度も見ていなかった**。
自分で確かめていたら「効いている」と誤読していた。

- **`EXIT` だけで判断しない。**`grep` で**落ちた検査の名前**まで確認する
- ⚠️ 検査を分担させたら、**分担の基準が一致しているか**を確かめる。
  上の2つは「実行時に choices を出すか」と「宣言が answerType!=choice か」で
  線を引いており、一致していなかった。**その隙間に落ちるものを誰も見ていない**
- 分担が複数あるなら、**隙間が無いこと自体を検査にする。**
  検査を足すたびに人が全部を思い出せる前提に立たない

## 対象外は、黙って落とさず理由つきで数える

⚠️ `if (total) skipped++` のように**対象外を条件付きで数えると、0件のものが消える。**
画面には「25テンプレートを調べた」とだけ出て、残り84本を見ていないことが読み手に分からない。

2026-09-08、**「0件で緑」を防ぐために書いた検査の中で、同じ罠を自分で作っていた。**

- 対象外にした件数は**必ず `cov.skipped()` に理由つきで出す**
- 理由には「どの検査が代わりに見ているか」を書く。書けないなら、それは穴

## 変異台帳は、ソースを直すと静かに腐る

⚠️ 変異の `find` は**ソースの文字列そのもの**なので、その行を書き換えた瞬間に一致しなくなる。
一致しない変異は**適用されないまま「壊しても落ちなかった」ではなく、そもそも試されない。**
台帳の件数は減らないので、数を見ている限り気づけない。

2026-09-07に**1日で7件**踏んだ。うち1件（「都市名の英語語彙を日本語に戻す」）は
その日の変更より前から死んでいて、`cities` を配列からオブジェクトに変えた時点で腐っていた。

**ソースを直したら、コミット前にこれを打つ**（1秒で終わる。全件実行は数十分かかる）:

```sh
node -e '
const fs=require("fs");const ms=JSON.parse(fs.readFileSync("test/mutations.json","utf8"));const c={};let miss=0;
for(const m of ms){if(!(m.file in c))c[m.file]=fs.readFileSync(m.file,"utf8");
 const n=c[m.file].split(m.find).length-1;
 if(n!==1){console.log((n===0?"❌ 空振り":"⚠️ "+n+"箇所")+": "+m.name);miss++;}}
console.log(ms.length+"件中 "+miss+"件が問題あり");'
```

- 変異ランナー本体も同じ検査を持っているが、**全件実行の中でしか回らない**。
  数十分待ってから「find が無い」と言われるのは遅すぎる
- 直したら**その変異を1件だけ当てて、狙った spec が落ちることを実測する**。
  台帳を直した「つもり」で終わらせない
- ⚠️ **他に赤がある状態で変異の実効性を確かめない。**落ちた原因が変異なのか
  元からの赤なのか区別できない。今回それで一度「✅」と誤読しかけた

## リポジトリの触り方

- ⚠️ **`git status` は statキャッシュで「クリーン」と嘘をつく。**`git show HEAD:<file> | cmp` か `git update-index --really-refresh` を先に打つ
- **本体ツリー `/Users/keita/Documents/spi-practice` には書かない。**自分の worktree を切る
- ⚠️ **変異ランナーは `nohup` で切り離す。**前景実行はツールのタイムアウトで SIGKILL され、変異が残る
- **ロック（`test/.mutation-runner.lock`）を見てから、リポジトリの状態を判断する**
- **`git add -A` を使わない。**変更したファイルを名指しで
- **待機タスクは1本まで。**複数仕込むと、解放時に同時発火して共有ツリーを壊す（実績あり）
- **報告のハッシュは、ブランチ先端と一致させる**（rebase で変わる）

## やらないこと

- **`git push` しない。**必要になったら報告する
- 🚫 **アフィリエイトURLを辿らない**（`px.a8.net` `h.accesstrade.net`）。文字列として扱うのは可。自己クリックは否認条件に抵触する
- 🚫 **`~/Documents/project-scanner/scan.py` を丸ごと実行しない。**`backup_repos()` が `git add -A` して private リポジトリに push する。読むのは可
- **`answerFormula` を読んでから、その答えを検証する検査を書かない。**同じ式が2箇所になるだけ。検査は問題文から導く

## 詰まったときの判断

- **「できるか」と「やるべきか」を分けて答える。**道具を拡張できても、複雑さの代償が上回るなら「足すべきでない」と言ってよい
- **判断がつかないものは「判断がつかない」と残す。**「たぶん大丈夫」で通さない
