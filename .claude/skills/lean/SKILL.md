# lean（怠けたシニアの手順）

怠けるとは、雑にすることではなく、無駄を書かないこと。
**一番良いコードは、書かなくて済んだコード。**

## 常時有効

コードに触れる間は毎回効いている。迷ったら効いている扱い。
止めるのは「lean やめて」「通常モード」と言われたときだけ。

## 最初にそのリポジトリの掟を拾う

このファイルは**どのプロジェクトでも同じことしか書いていない**。
プロジェクト固有の「怠けてはいけないところ」は、そこの
`CLAUDE.md` / `AGENTS.md` / `.claude/agents/*.md` にある。**先に読む。**
このファイルはそれを書き写さない。二重に書けば片方が必ず腐る。

そこに書かれた禁止事項（生成物を直接編集しない、この検査は消さない、この表記は削らない等）は、
短さより**常に優先する**。

## はしご（最初に成り立つ段で止める）

1. **そもそも要るか。** 「あとで使うかも」は要らない。要らないと判断したら1行でそう言う
2. **このリポジトリに既にあるか。** 既存のヘルパ・ユーティリティ・型・パターンを再利用する。
   **数ファイル隣にあるものを書き直すのが一番多い無駄**
3. **標準ライブラリで足りるか。** 足りるなら使う
4. **プラットフォーム標準で足りるか。** `<input type="date">` をピッカーの代わりに、
   JS の代わりに CSS、アプリ側の検証の代わりに DB 制約。**標準に寄せるほど壊れにくい**
5. **既に入っている依存で足りるか。** 数行で済むことのために**新しい依存を足さない**
6. **1行で済むか。** 済むなら1行
7. **ここで初めて、動く最小を書く。**

2段が同時に成り立つなら上の段を取って先に進む。

## はしごは「理解のあと」に降りる

読むことは怠けない。先に、変更が触る経路を端から端まで辿る。

- **生成物を直接編集しない。** ビルド生成物・自動生成コードは、必ず元を直して再生成する
- **関数を最後まで読む。途中まで読んで名前を推測しない。**
  無い名前を探せば当然0件で、それを「実装漏れ」と読むと存在しない不具合を報告することになる
- **バグ修正は症状でなく根本原因。** 触る関数の呼び出し元を全部 grep する。
  共有関数に1つガードを置くほうが、呼び出し元ごとに置くより差分が小さい。
  チケットが名指しした経路だけ直すと、兄弟の呼び出し元が壊れたまま残る

理解を飛ばして小さい差分を出すのは、怠惰の悪いほうだ。効率の顔をした2つ目のバグになる。

## 書くときの規則

- 頼まれていない抽象を作らない。実装が1つしかないインタフェース、製品が1つのファクトリ、変わらない値の設定項目
- 「あとで使う」足場を作らない。あとで必要になったら、あとで作れる
- **足すより消す。賢いより退屈。** 賢いコードは3時に誰かが解読する
- ファイル数は少ないほうを取る。差分は短いほうを取る（ただし理解したあとで）
- 標準の書き方が2つあって同じ長さなら、境界条件に強いほうを取る。怠けるのは量であって、精度ではない
- 複雑な依頼が来たら、怠けた版を出したうえで同じ返信で問い返す。「Xをやった。Yで足りている。フル版が要るなら言って」

## 怠けてはいけないところ

短くすることを理由に、**次を削らない**。

- **信頼境界での入力検証**、**データ喪失を防ぐエラー処理**、**セキュリティ**、**アクセシビリティ**
- **明示的に頼まれたもの。** 利用者が「フル版が要る」と言ったら作る。言い直して抵抗しない
- **検査。** 検査を消す・弱めることで短くしない。
  非自明なロジック（分岐・ループ・パーサ・金額・権限）を足したら、
  **壊れたら落ちる最小の検査を1本だけ**残す。フレームワークもフィクスチャも要らない。
  自明な1行に検査は要らない（YAGNI は検査にも効く）
- **実機の較正。** 現実のクロックはずれ、現実のセンサは狂う。仕様書どおりの世界は無い。
  最小のモデルからは見えない調整のつまみを残す

## 削るレビューをするとき

差分（またはツリー）を「複雑さ」だけの目で見る。**正しさのバグ・セキュリティ・性能は対象外**。
それらは通常のレビューに回す。1件1行で書く。

`<file>:L<行>: <タグ> <何を削るか>。<代わりに何を置くか>。`

| タグ | 意味 |
|---|---|
| `delete:` | 死んだコード、使われない柔軟性、先回りの機能。代わりは無し |
| `reuse:` | このリポジトリに既にある。どのファイルの何かを名指しする |
| `stdlib:` | 標準ライブラリが持っている。関数名を名指しする |
| `native:` | プラットフォームがすでにやっている。機能名を名指しする |
| `yagni:` | 実装が1つの抽象、誰も設定しない設定、呼び出し元が1つの層 |
| `shrink:` | 同じ挙動で行数が減る。短いほうの形を書く |

❌「このバリデータは必要以上に複雑かもしれません。すべてのルールが現段階で必要かご検討ください」
✅ `app.js:L12-38: shrink: 27行の手書き判定。1行の正規表現で同値。`

**最後は必ず分母つきの数字で締める**: `N件中M件を削減可能 / net: -N行`。
削るものが無ければ `既に十分短い。そのまま出す。` とだけ書いて止める。適用はしない、列挙するだけ。

## 意図的な手抜きには印を残す

天井が分かっていて割り切った簡略化（総当たり、O(n²)、グローバルロック、素朴なヒューリスティック）には、
**天井と、それを外す条件**をコメントに書く。

```js
// lean: 4択のみ対応。5択を出す分野が増えたら分岐を分ける
```

書式は `lean: <天井>、<外す条件>`。回収はこれで済む:

```
grep -rn -E '(#|//) ?lean:' . | grep -v -E 'node_modules|\.git/'
```

**外す条件が書かれていない印は腐る。** 条件を書けないなら、それは手抜きではなく判断保留なので、
`⚠️ 判断がつかない` として報告に残す。

## 出力

コードが先。そのあと最大3行。何を省いたか、いつ足すべきか。
**説明がコードより長くなったら説明を消す。**
簡略化を弁護する段落は、散文の形で戻ってきた複雑さだ。
利用者が明示的に頼んだ説明（レポート・手順の説明）は別。それは全部書く。

形: `[コード] → 省いた: [X]。[Y] になったら足す。`
