# 欠陥の性質カタログ

**使い方**: 新しい機能・検査を足したとき、この一覧を上から当てる。
各性質は**質問の形**で書いてある。答えは必ず「**N件中M件**」で出す。
⚠️ **0件のときは分母を示すこと。**「壊れているものが無い」と「何も見ていない」は別。

**このカタログの限界**: ここにあるのは**一度遭遇した型だけ**。
新しい型を思いつく作業は自動化できていない。できるのは
**「一度会った問題に二度と時間を使わない」ことまで**。

---

## A. 検査が黙る（2026-08-28〜29 に8回）

### A1. 検査が、検査対象から基準を作っている
**問い**: その検査の閾値・許容幅・期待値は、**検査したい対象そのもの**から導いていないか。
- 実例: 解説の検算が、許容幅を「**表示された桁数**」から作っていた。丸めを見つけたい検査が、丸めた表示から基準を作るので原理的に捕まらない
- 実例: 正解位置の偏りをσで判定 → σは症状。原因（同点）を直接見たら28%の圧倒的な信号だった
- **直す方向**: 比較相手ではなく、**あるべき値**と突き合わせる

### A2. 比較する2つが、たまたま同じものを指している
**問い**: 「AとBが一致すること」を確かめる検査で、**AとBが同じ出所**になっていないか。
- 実例: 注記の検査が2件を比較していたが、比較対象がたまたま同一だったので条件が偽になり素通り
- **直す方向**: 出所が独立していることを、検査自身が確かめる

### A3. ガードが2枚あって互いを隠す
**問い**: 片方を壊したとき、もう片方が代わりに止めてしまわないか。
- **直す方向**: **1枚ずつ壊して、それぞれ落ちること**を確かめる（＝変異テスト）

### A4. 遅れて足した処理が、結果に反映されない
**問い**: 出力・集計・終了コードを決める箇所より**後ろ**に足していないか。
- 実例: `fail()` が配列に積むだけで、配列は「出力」節で1度だけ読まれる作りだった。**出力節より後に足した検査2本が、足した瞬間から無効だった**（検査自身の ❌ を印字しながら EXIT=0）
- **直す方向**: 記録した時点で結果に反映する。**「後から足しても効く」形にする**
  （直した形: `fail()` が呼ばれた時点で `process.exitCode` を立て、印字漏れは `reportLateFailures()` が最後にまとめて拾う。test/generator.spec.js）

### A5. 書かれているのに実行されない
**問い**: その検査・設定・分岐は、**実際に走っているか**。
- 実例: `affiliate.spec.js`（景表法のPR表記を守る検査）が **CI で一度も走っていなかった**
- 実例: spec の中で条件が満たされず一度も実行されない検査ブロック
- **直す方向**: ファイル一覧と実行設定を**機械的に突き合わせて落とす**（`wiring.spec.js`）。手で二重に書かない

### A6. 見送り（skip）が、途中で意味を変える
**問い**: 「まだ無いから見送る」と書いた箇所は、**有るようになった後も見送っていないか**。
- 実例: `cov.skipped("属性ごとの枠", 0, "素材が未投入")` が素材投入後も残り、**属性の出し分けが丸ごと消えても緑**だった
- ⚠️ **これは「最初から間違い」ではなく「途中で意味が変わった」型。レビューでは捕まらない**
- **直す方向**: **見送る条件を、見送る理由そのもので判定する**（素材が0件のときだけ見送り、素材があるのに枠が0なら失敗）

### A7. 例外リストが腐る
**問い**: 免除・例外・TODO に、**一括の文言**が使われていないか。
- 実例: 台帳（mutations-uncovered.json）130件すべてが「初期移行分」の一文。**「書けない」と「書いていない」が区別できていなかった。**仕分けたら「書けない」は3件しかなく、105件は「まだ書いていない」だった
- **直す方向**: **個別の理由を必須にする。理由が個別に書けないなら、それは例外ではない**
- ⚠️ **「書けない」は道具の制約に相対的。**「原理的に不可能」なのか「いまの道具（内容置換の変異）では不可能」なのかを理由に書き分ける。道具が変われば例外でなくなるものを、永久の免除に見せない

### A8. 一括で承認・無効化できる口がある
**問い**: 「全部OKにする」を1コマンドで打てないか。
- 実例: `UPDATE_BASELINE=1` で63件が一括更新。**無関係な揺らぎも、実在する退行も、まとめて承認される**
- **直す方向**: 塞ぐのではなく**安全な口を用意する**（名指し更新＋理由必須＋タイポ検出）。禁止すると手書きになり、手で書けば書き間違える

## B. 数え方が間違っている

### B1. 名前で数えている（grepの一致を証拠にしている）
**問い**: その件数は、**動作で測ったか、名前で測ったか**。
- 実例: 「どの検査からも参照されていない定数」を grep で数えると **65件中52件**、実際に潰して測ると **1件**
- 実例: 「推論不要」を目視で42% → 定義して機械で数えて **61.0%**
- **直す方向**: **潰して落ちるかで測る。** ⚠️ 壊し方の強さも申告する（「丸ごと空にする」で落ちない件数と、「1要素だけ変える」で落ちない件数は別物）

### B2. 個別に指名して、性質で掃いていない
**問い**: 見つけた1件を、**性質に一般化して全件に当て直したか**。
- 実例: 「未約分の比を2件」と指名 → 検査を先に書いたら**実在4件**
- 💡 **先に検査を書くと、指示した側の範囲指定が不完全であることを機械が暴く**
- **直す方向**: 指名を受けたら「**その性質で全件を掃いたら何件ですか**」と返す

### B3. 分母を見ていない
**問い**: 「0件でした」の**0は、分母がいくつのうちの0か**。
- 実例: 掃き出しの出力が `0件 / 0件`。正規表現に `re.M` を付け忘れ、**1件も拾えていなかった**
- **直す方向**: 対象が想定より少なければ**異常終了する**ガードを入れる

## C. 出力と実体がずれる

### C1. 同じ事実を2箇所に手で書いている
**問い**: その数値・名前は、**実データから導けないか**。
- 実例: 「10分野」が全17ページに散在、実際は13分野。**一度直したとき本文だけ直し、メタとJSON-LDを意図的に残した → 再発**
- **直す方向**: **数を書かない表現にする**か、**1箇所に置いて他が読む**（`ANSWER_DECIMALS` を app.js に置き、検査が読む）

### C2. 存在しないものを宣伝している
**問い**: title・description・構造化データが約束している内容は、**実在するか**。
- 実例: `/categories/` が「10分野それぞれの解き方」と検索結果に出して、**実在3本**
- **直す方向**: 実データ（存在するページの一覧）と突き合わせて落とす

### C3. 状態の判断を、1つのコマンドの出力に預けている
**問い**: その「クリーン」「成功」は、**中身を見た結果か**。
- 実例: `git status` は (mtime, サイズ, inode) のキャッシュで**中身を読まずに「クリーン」を返す**
- 実例: `EXIT=1` は「**何かが**落ちた」であって「**狙ったものが**落ちた」ではない
- **直す方向**: `git show HEAD:<file>` のバイト比較。**狙った失敗メッセージが出るところまで見る**

## D. 問いのほうが壊れている

### D1. 答えは正しいが、問いが成立していない
**問い**: 生成された問題は、**問いとして選ぶ余地があるか**。
- 実例: 集合の「最も多い場合」で、片方が全員だと重なりの幅がゼロに潰れる（13.5%）
- 実例: 推論問題の**61%が推論不要**（条件に全対戦結果が並ぶ／引き算で出る）
- ⚠️ **答えを見る検査では原理的に捕まらない**
- **直す方向**: **問題文そのものを読んで**判定する（内部変数でなく、利用者が見る文面で）

### D2. 設問が2つのことを聞いている
**問い**: 設問文に、**単位や形式が2つ**書かれていないか。
- 実例: 「何時間何分かかるか。（**分単位で答えよ**）」
- **直す方向**: 答えの形に問いを揃える

### D3. 判定が答えの刻みより粗い
**問い**: 正解どうしの**最小間隔**は、判定の許容幅より広いか。
- 実例: 濃度算は答えが0.1刻みなのに許容幅0.15。**正解8に対し7.9でも「正解」**（6テンプレート）
- **直す方向**: 許容幅ではなく**精度**で判定する

## E. 計測が嘘をつく

### E1. 発火条件が満たされないまま「計測している」ことになっている
**問い**: そのイベントは、**実際に飛んでいるか**。
- 実例: 読了深度がスクロール率依存で、**画面に収まる短い記事では25%すら出ない**。GA4では「読まれていない」に見えるが実際は「**測れていない**」
- **直す方向**: DOMを与えて**発火を実測する**検査を書く

### E2. 冪等でない操作が二重に記録される
**問い**: 利用者が**連打・二度押し**できる操作のうち、冪等でないものは何件か。
- 実例: 14操作中6件（`exam_start` `retry_exam` `review_start` `share_x` `report_error`）
- ⚠️ **時間窓（700ms等）で切ってはいけない。速い利用者と二度押しは時間で区別できない**
- **直す方向**: **対象の同一性**で見分ける

## F. 作業の進め方

### F1. 測った事実と推測した事実が、要約を通ると同じ顔になる
- 実例: 存在しないコードを疑わせた／grep由来の誤りを既知として渡した／中身を見ずに危険と判断した（1日で3回）
- **直す方向**: 渡すときに「**測った / 監査由来 / 推測**」を明示。出どころが言えないなら渡す前に測り直す

### F2. 自分の副作用を追跡していない
- 実例: 「ロックが空いたら検証する」ジョブを3回仕込んで回収せず、**朝3組が同時発火して共有ツリーを壊した**
- 実例: 唯一の写しを一時領域に置き、消えた
- **直す方向**: **待機ジョブは1本まで。** 定期的に自分のプロセス・worktree・常駐を棚卸しする。**唯一の写しを一時領域に置かない**（コミットが唯一の耐久記憶）

### F3. 自分の作ったものを自分で試験する
- ⚠️ A1 と同じ構図が作業手順にも出る。**「壊したら落ちる」の確認を、壊した本人の目視だけで済ませない**
- 実際の分担: 書いた本人は**機械的な検証**（狙った失敗メッセージが出るまでを、目視でなくハーネスで確認）までは行う。**最終の合否判定と公開の判断は、書いた本人以外が実測する**
- **直す方向**: 「本人の機械検証 → 第三者の実測」の二段。どちらか片方では、A1（対象から基準を作る）と同じ盲点が残る
